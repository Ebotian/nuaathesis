# “阶段时间线（全周期）”详细分析

## 1. 分析目的

本文用于支撑 [main.tex](/home/ebit/endofnuaa/texppt/main.tex:78) 中“阶段时间线（全周期）”这一页，但分析方法不再局限于最近三周，而是基于完整主线 `git log --oneline --graph --decorate --all`，从 `Initial commit` 一直梳理到 `HEAD`。

这样做的原因很直接：

- 只看 `W07 / W11 / W12` 会得到“近期阶段结论”。
- 但如果要解释“项目到底是怎么一步步走到今天的”，就必须看完整提交链。

因此，这份文档分成两层：

1. 先给出完整历史下的“全阶段流程”。
2. 再把完整流程压缩映射回 PPT 当前使用的三段时间线。

## 2. 分析依据

本分析主要基于以下证据：

- 完整主线提交记录：
  - 从 `c9fa960 Initial commit`
  - 到 `acb4ef3 代码类型更新`
- 关键里程碑提交标题及其先后关系。
- `正式文档/2026-W07`、`正式文档/2026-W11`、`正式文档/2026-W12` 的文档主题。
- 前端 `src/components` 与后端 `electron/*` 的改动重心变化。

说明：

- `正式文档` 的周目录是在后续整理时归档形成的，所以它更适合做“阶段主题”的佐证，而不是用来机械代表最初写作日期。
- 完整阶段判断的主证据仍然是整条 `git` 主线本身。

## 3. 总体判断

从完整历史看，这个项目并不是简单的“三周做了三件事”，而是经历了一个比较清晰的五阶段推进过程：

1. 需求确认与方向建立
2. UI 底座与界面骨架搭建
3. 参数化面板与基础展示完善
4. 通信链路与后端能力打通
5. 测试方法、实验设计与算法表达深化

如果再进一步压缩，这五阶段又可以归纳成三层推进逻辑：

`先明确要做什么` -> `再把系统搭起来并跑通` -> `最后让测试方法变得可解释、可验证、可扩展`

这也是你 PPT 那条时间线背后的真正工程逻辑。

- 修正需求。

这说明项目启动时的核心矛盾不是“不会写代码”，而是“问题边界还没有完全稳定”。在这种情况下，频繁确认需求是合理的，因为桌面测试系统本身牵涉 UI、硬件协议、测试功能、展示逻辑，前期不收口，后面就会不断返工。

因此，项目真正的第一个里程碑不是某个界面，而是“需求已经足够清楚，可以进入设计和实现”。

## 5. 从完整历史反推当前 PPT 时间线

现在再回到 [main.tex](/home/ebit/endofnuaa/texppt/main.tex:78) 的“阶段时间线（全周期）”这一页，就会发现：

- PPT 写的是三段。
- 实际历史更像五段。

这两者并不矛盾，因为 PPT 本来就是“汇报压缩版”，它不会把所有阶段都逐条展开。

### 5.1 第一周：架构与规范固化

这并不只是 `W07` 那几份文档，而是完整历史里以下阶段的压缩：

- 阶段一：需求确认与项目起步
- 阶段二：UI 底座与界面骨架搭建
- 阶段三前半段：参数化面板设计、TDD 思路、基础展示规范

所以，“架构与规范固化”本质上是在压缩表达：

- 需求收敛
- UI 体系建立
- 基础架构与开发方式明确

它不是狭义的“只改了两个配置文件”，而是整个项目的底层规则在这一阶段逐渐成型。

### 5.2 第二周：需求细化与任务分解

这主要对应完整历史里的阶段四前半段：

- 发送逻辑
- 串口整合
- 串口连接
- 真实后端测试前的准备
- 协议与 worker 设计任务的明确

所以这页 PPT 上的“需求细化与任务分解”其实应理解成：

- 项目从“系统长什么样”转向“每个工程节点怎么做”。
- 需求开始不再停留在说明文档，而是直接牵引具体实现顺序。

### 5.3 第三周：算法深化与可实现化

这主要对应完整历史里的阶段四后半段与阶段五：

- 真实后端测试成功
- 进入信号发生器设计阶段
- 测试实验设计
- 预实验 UI
- 时域 UI 框架
- 后端需求整理
- 代码类型统一

因此，这一周真正表达的不是“突然开始做算法”，而是：

- 在链路已经基本打通之后，项目开始把测试方法做实。
- 算法、实验设计、前端展示、后端结构开始同时收敛。

## 6. 为什么必须看完整 Git 历史

如果只看最近三周，会有两个问题：

### 6.1 会低估前期 UI 与结构工作的价值

因为从近期视角看，容易误以为项目一开始就直奔测试算法。但完整历史表明，前期其实投入了大量工作在：

- UI 布局
- 响应式
- 参数输入框架
- 数据显示
- 信号显示
- 面板扩展

这些工作虽然不像“算法设计”那样显得学术，但它们是整个测试系统能够承载后续方法论的基础。

### 6.2 会误读“算法深化”的含义

因为算法深化并不是凭空出现的。它是在下面这些条件都基本具备后才开始成立：

- 已经有了可交互的 UI。
- 已经有了基本的数据展示能力。
- 已经有了串口和发送链路。
- 已经出现了真实后端测试成功。

所以，算法深化不是一个孤立事件，而是完整工程链条上的后继阶段。

## 7. 对“全阶段流程”的简洁概括

如果用一句话概括整条 `git` 主线，可以写成：

> 项目从需求确认出发，先完成桌面测试系统的 UI 骨架与参数化界面，再逐步补齐数据展示、串口通信与真实后端链路，最终进入测试实验设计、时域/频域方法实现与后端结构整理阶段。

如果用更适合答辩口述的版本，可以写成：

> 整个项目不是直接从需求跳到算法，而是先把系统外形和交互底座搭起来，再把通信和实际测试链路跑通，最后才进入测试方法本身的深化与工程化实现。

## 8. 对当前 PPT 页的建议

你现在的三行时间线没有问题，但它本质上是“高压缩版”。如果你担心导师追问“为什么这样分”，可以直接用下面这套解释：

- 第一周对应的是前期需求、UI 规范、架构思路和参数面板框架的收敛。
- 第二周对应的是协议、串口、发送、Worker、真实后端测试这一组链路的打通。
- 第三周对应的是测试实验设计、预实验、时域/频域 UI、后端需求整理与类型统一。

如果你愿意把 PPT 文案再改得更贴近完整历史，我建议使用下面这个版本：

- 第一周：底座建立与规范收敛
- 第二周：通信链路打通与工程验证
- 第三周：测试方法深化与算法落地

这一版比“架构与规范固化 / 需求细化与任务分解 / 算法深化与可实现化”更贴近完整 `git` 历史，也更容易被评审快速理解。

## 11. 局限性说明

这份分析尽量依据完整 `git` 主线来做，但仍然有两个边界：

- 部分提交标题比较口语化，例如“暂时可行”“好吧这才是预实验UI”，其阶段含义需要结合上下文理解。
- 依赖更新类提交和合并提交存在，但它们不是这条工程主线的核心，因此本文只把它们作为背景，不作为主结论依据。

即便如此，从完整提交主线看，“先搭底座、再通链路、后做方法”的结论是非常清楚的。
