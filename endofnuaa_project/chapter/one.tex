\chapter{绪论}

\section{背景和意义}

舵机是一类典型的机电执行机构，控制系统输出的指令最终要落实为角位移、角速度或力矩响应。在航空航天、自动控制和工业装备等场景中，它通常处在控制链路末端，动态响应、稳态误差、重复性和通信稳定性的波动都会传递到上层控制效果。对精密舵机来说，单次动作完成只是最基础的一步；在连续指令、不同激励形式和不同测试流程下，系统还需要保留可观测、可分析和可追溯的工作状态。国内伺服测试平台和工业测试系统研究已经把测试对象、控制链路、数据处理和结果管理放在同一流程里讨论\cite{li2014servotest,xu2021industry4test,liu2022industrialsoftware}。

测试现场中的软件任务具有不同的时间尺度。串口反馈和帧解析需要跟随硬件节奏，参数输入、测试项切换和结果查看则由人工触发。两类过程进入同一执行上下文时，界面响应、数据缓存和状态更新容易相互影响。数据采集软件和在线分析系统的相关研究强调采集、处理、展示和分析之间的职责划分，原因在于实时数据流需要稳定的软件边界\cite{stansbury2023autodidaqt,turkmanovic2023highspeed}。

本课题最终实现的软件运行在 Windows 环境下，通过 RS422 与舵机控制器通信。前端用 Vue3 搭建参数输入和数据展示页面，后端由 Electron 主进程、预加载脚本和 Worker 组织串口通信、数据处理和测试执行。软件把协议解析、实时显示、通信性能测试、控制性能预测试、时域性能测试、频域性能测试和结果保存放入同一条测试流程，界面与后台各自处理不同粒度的任务。

工程实现上，本文关注的是软件内部如何把这些环节接起来。高频反馈由后台任务和测试核心处理，界面层保留参数输入、状态查看和结果操作；协议差异收敛在帧构造、帧解析和校验环节，测试算法只面对结构化反馈样本；预测试参数、时域指标、频域指标和结果文件沿同一链路传递，便于追溯每一步数据从哪里来、经过了哪些处理。

本文以当前已经完成的软件系统为研究对象。软件定位为精密舵机桌面测试工具，早期方案中尚未落地的其他测试内容只作为需求演化背景。正文重点放在四类已经实现的测试功能上：通信性能测试、控制性能预测试、时域性能测试和频域性能测试。24 h 连续运行、完整端到端延迟等缺少独立实测支撑的指标，只在设计目标、实现约束或后续工作中讨论，不写成已经验证的结论。

\section{国内外研究现状}

本课题涉及执行机构测试、工业数据采集软件、串口通信可靠性和自动测试方法等多个方向。现有文献较少直接讨论基于 Electron 的多协议舵机测试软件，因此本节按本文要解决的几个问题归纳相关研究，并说明其中可借鉴的内容和仍需结合本课题展开的部分。

\subsection{执行机构测试平台与硬件在环研究}

执行机构测试平台研究的重点，是在可控条件下重现对象工作过程，并据此测量动态特性、负载响应和控制性能。李敬孔围绕伺服系统测试平台的设计与实现讨论了测试对象分析、平台功能组织和结果处理，为本文理解伺服类对象的测试软件边界提供了国内参考\cite{li2014servotest}。Anastasopoulos 和 Hornung 针对无人机舵机执行器设计实时测试台，关注执行器在测试环境下的动态响应测量\cite{anastasopoulos2018uavbench}。Dell'Amico 面向航空执行机构提出硬件在环空气载荷模拟系统，通过更接近真实工况的载荷复现来验证执行机构性能\cite{dellamico2024airloadhil}。

国内围绕单对象控制实验平台也积累了较多工作。林立等设计了集成 DSP 控制器和上位机监控界面的异步电机直接转矩控制实验平台，周晓华等利用 Matlab/Simulink 构建永磁同步电机矢量控制仿真实验，张惠国等则将低压直流无刷电机控制系统组织为综合性实验平台\cite{lin2025dtcplatform,zhou2020pmsmexperiment,zhang2016bldcexperiment}。这些研究虽然主要服务于教学验证或单对象实验，但共同点都是把控制回路、反馈采集、上位机界面和实验流程放在一套系统里处理。

这些平台研究把执行机构测试从单次测量扩展到工况设置、激励生成、反馈采集和性能分析等环节。舵机测试软件在其中承担的是软件组织层工作，要把硬件链路接起来，也要把测试过程和结果说明清楚。

在执行机构控制策略方向，汪春阳针对电液位置伺服系统研究了滑模、有限时间和预设性能控制，并通过实验验证控制效果；王超则面向重载电液伺服驱动机器人研究末端拖拽控制与阻抗控制策略\cite{wang2025electrohydraulicsmc,wang2025hydraulicdrag}。这类工作说明，国内研究已经在特定执行机构的控制品质提升和实验验证方面形成较深积累，但其重点仍然集中在单对象控制器设计，对多协议桌面测试软件流程组织的讨论相对有限。

已有执行机构测试平台多依附于专用测试台、加载装置或固定对象，软件部分通常服务于特定实验系统。面向桌面软件时，多协议解析、高频反馈流、测试项切换和结果保存会集中到同一程序内部，而这类组织问题在已有研究中讨论得并不充分。本文因此把重点放在精密舵机测试软件的架构划分和测试流程组织上。

\subsection{工业桌面测试系统架构与实时数据采集研究}

设备测试软件需要处理持续到达的数据流，也需要响应用户操作、展示曲线并保存结果。随着测试对象和数据规模增加，传统单线程或单流程界面程序在实时性和可维护性之间承受更大压力。徐景辉等从工业 4.0 条件下的测试系统出发，指出测试系统正在向自动化、网络化和信息融合方向发展\cite{xu2021industry4test}。刘务等关于工业软件测试验证体系的研究强调，工业软件需要通过规范化验证链路保证可靠性\cite{liu2022industrialsoftware}。Stansbury 和 Lanzara 提出的 AutodiDAQt 将数据采集与在线分析结合，强调科学数据采集软件应支持并发、可复现、采集过程回溯和自动化界面生成\cite{stansbury2023autodidaqt}。Turkmanovi\'c 等针对远程高速数据采集提出高性能软件架构，指出低延迟传输和实时显示同时受硬件链路、软件端任务划分和数据处理方式影响\cite{turkmanovic2023highspeed}。

国内研究也为桌面测试软件的技术选型提供了参考。张子磐围绕 Qt 测控软件开发讨论了桌面测控系统中的采集、控制和界面集成问题\cite{zhang2017qtflowmeter}。高雨等讨论了基于 Electron 框架构建跨平台数据采集桌面应用的方法，说明 Web 技术栈在桌面数据采集软件中具有界面开发效率和跨平台部署优势\cite{gao2025electron}。在此基础上，前端界面采用组件化方式组织不同测试面板和结果区域，使通信选择、参数输入、控制与数据显示能够围绕同一测试流程协同展开。这些研究虽不直接面向舵机测试，但能够支撑本课题所设计软件在桌面框架选择与界面组织方式上的合理性。

相关工作显示，桌面测试软件至少需要处理三类关系：采集与显示的边界、后台处理与界面响应的边界、临时数据与可追溯结果的边界。本文采用渲染进程、主进程、预加载桥接和 Worker 模块组织这些关系，使高频反馈数据和低频测试控制逻辑分别进入合适的执行位置。

\subsection{RS422/UART 串口通信与可靠传输研究}

通信链路是舵机测试软件的基础。只有控制指令能够正确发送、反馈数据能够稳定接收、帧边界能够识别、字段能够解析并完成校验，后续测试算法和可视化结果才有意义。所设计的软件系统通过 RS422 与舵机控制器连接，论文重点关注串口链路之上的协议解析、帧校验和结构化数据表达。

在公开研究中，直接讨论 RS422 多协议舵机测试软件的文献较少。与本文更接近的中文研究多分布在测控软件和串口通信实现方向。张子磐关于 Qt 测控软件开发的研究说明，桌面测控系统通常需要在设备通信、数据采集、界面显示和结果管理之间建立清晰接口\cite{zhang2017qtflowmeter}。吴浩松等研究了基于数据分包的嵌入式串口通信方法，指出在连续数据流中合理的分包、缓存和校验机制有助于提高通信稳定性\cite{wu2025serialpacket}。胡腾飞等围绕 RS422 总线接口误码测试系统开展设计，说明上位机、总线接口和误码统计可以共同服务于通信质量评价\cite{hu2026rs422ber}。

在可靠性方面，串口链路的稳定性同时取决于物理接口和上层软件对帧边界、缓存区、校验结果及异常数据的处理方式。对于舵机测试软件而言，通信模块需要把原始字节流转换为结构化反馈数据，并在解析失败、半包、粘包或校验错误时给出明确处理结果。串口通信研究为所设计的软件系统建立 RS422 反馈帧解析、缓存重组和错误上报机制提供了基础参考。

对本文而言，RS422 只提供底层传输条件，桌面软件还需要在其上建立协议处理机制。本文围绕同步字节、帧长度、控制量字段、反馈量字段和校验规则组织解析流程，并把解析结果整理为统一反馈结构，供可视化和测试算法复用。现有研究更多集中在串口基础机制、硬件实现或单一协议场景，多协议配置、半包及粘包处理、解析错误上报和业务层数据复用仍需要结合具体软件展开。

\subsection{自动测试、时域/频域评估与实验设计研究}

舵机测试软件除了要解决通信和界面问题，还要回答“如何测试”的问题。测试参数完全依靠人工经验填写，结果会受到人为差异影响；点位、频率和重复次数过多，又会拉长测试时间。自动测试方法必须在测试质量、统计可靠性和执行时间之间取得平衡。

在动态特性评估方面，Cajetinac 等通过 PWM 控制和频率特性辨识研究气动执行器，说明执行机构频域测试需要同时处理激励信号、采样过程和结果计算之间的关系\cite{cajetinac2012pwm}。国内工业测试系统和工业软件测试验证研究也指出，测试系统应兼顾测试流程规范、结果可追溯和工程现场使用效率\cite{xu2021industry4test,liu2022industrialsoftware}。

测试软件需要把测试参数、激励设计、数据采集和指标计算放入可解释流程。本文在时域测试和频域测试前设置预测试，先估计噪声水平、响应时间等中间量，再用于正式测试中的窗口长度、重复次数、采样时长或频点配置。频域测试通过正弦激励和相关分析提取幅值与相位；时域测试围绕调节时间、超调量、稳态误差和对称性组织结果。论文重点讨论这些方法进入桌面测试软件后的执行流程、实时显示和结果保存方式。

已有成果分别覆盖执行机构测试平台、实时数据采集软件、串口可靠通信和自动测试方法。精密舵机桌面测试软件需要把这些内容落到同一程序中：协议解析要服务测试算法，高频数据处理要避开界面阻塞，四类测试结果还要进入保存和复查过程。本文的工作从这一交叉位置展开。

\section{本文主要工作}

本文围绕精密舵机测试软件完成系统结构、通信链路、测试流程和结果管理设计。软件采用 Electron、Vue3 和 TypeScript 技术栈，前端负责参数输入、测试项选择、数据显示和结果交互；后端通过主进程、预加载脚本和 Worker 模块组织串口通信、测试任务和渲染数据整理。这样做以后，界面交互、高频数据处理和测试逻辑分别落在不同模块里，连续反馈到达时调用边界仍然清楚。

在通信与测试功能实现方面，软件先建立 RS422 串口通信链路和协议解析机制，再围绕四类测试功能组织核心流程。串口端口选择、连接管理、控制帧发送、反馈帧接收、字段解析和校验处理都在同一通信链路内完成，原始反馈被整理成上层模块可复用的结构化数据。通信性能测试统计发送和接收成功率以及采样间隔，控制性能预测试估计噪声水平、响应时间和运动速度，时域性能测试分析调节时间、超调量和稳态误差，频域性能测试则通过扫频和相关法估计幅频、相频特性并形成伯德图结果。

软件还保留了实时可视化和结果管理功能，包括四通道遥测显示、示波器曲线、时域图表、频域伯德图、测试结果保存和历史数据加载。工程验证阶段设置了串口解析、协议合规、信号发生器、通信性能测试、时域测试和频域测试等单元测试，并补充了面向真实硬件的后端冒烟测试和实机测试脚本。本文把软件架构、通信链路和测试流程组织作为主要工作，测试材料则用于说明系统实现的正确性和可维护性。

\section{论文组织结构}

全文共分为七章。第一章说明课题背景、研究现状和本文工作范围，并将执行机构测试平台、桌面数据采集、串口通信和自动测试方法归并到舵机测试软件设计问题中。第二章根据当前软件状态梳理通信接入、状态确认、四类测试、数据显示和结果管理需求，同时说明 Electron、Vue3、TypeScript、IPC、Worker 和串口通信机制的使用依据。

第三章在需求约束下给出分层架构、层间契约、IPC 事件流、前端界面和后端调度设计。第四章沿着总体架构中的数据通路展开，说明 RS422 链路、两类协议帧、发送队列、接收缓存、使能检测和信号发生器设计。第五章在通信与基础控制能力之上描述四类测试算法，重点说明通信测试、预测试、时域测试和频域测试之间的参数传递关系。

第六章把前述设计落实到工程实现和验证材料中，说明界面、主进程、后台任务、通信模块、测试核心和结果保存之间的运行关系，并根据自动化测试和实机检查给出当前可用范围。第七章总结已完成工作，说明长期稳定性、完整端到端时延、图片导出和更多协议适配仍属于后续完善内容。
