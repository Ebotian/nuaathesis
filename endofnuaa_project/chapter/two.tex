\chapter{需求分析与相关技术}

\section{需求来源与软件边界}

精密舵机测试软件的需求来自现场操作顺序。测试开始前，操作人员先确认通信链路是否可用；测试运行时，软件要发送控制指令、接收反馈并显示状态；测试结束后，结果还要保存下来，供异常复查使用。伺服测试平台研究通常把功能测试、性能测试和测试流程作为整体方案处理，工业测试系统和工业软件验证研究也把流程规范、数据管理和可靠性验证放在一起讨论\cite{li2014servotest,xu2021industry4test,liu2022industrialsoftware}。单次采集程序难以支撑这种连续测试任务。

在本课题中，软件边界由测试对象和工程条件共同确定。系统运行于 Windows 环境，通过 RS422 串口链路与舵机控制器通信；界面层采用 Vue3 组织参数输入和结果展示，后台侧由 Electron 主进程、预加载脚本和 Worker 模块承担串口访问、任务调度和数据处理。最终稳定下来的功能是通信性能测试、控制性能预测试、时域性能测试和频域性能测试，界面中的测试选择也按这一顺序组织。早期方案中的其他测试设想只作为需求演化来源，不写入当前软件已经完成的功能边界。

本章按一次测试任务的实际路径展开需求分析：先建立通信链路，再确认设备状态，随后在不同测试目标之间传递参数，最后把结果数据送入显示、保存和复查过程。后续架构设计、通信模块和测试算法均围绕这条路径展开。

\section{功能需求分析}

功能需求需要贴合现场操作顺序。一次完整的舵机测试通常从串口连接开始，经过使能检测和基础控制确认，再进入测试任务选择与参数设置；正式测试完成后，软件还要把反馈数据转化为图形、指标和可保存结果。各项功能之间存在明确的前后依赖。

\subsection{通信接入与协议适配需求}

测试流程的入口是通信接入。软件应提供串口枚举、端口选择、波特率设置、协议版本选择以及连接和断开操作。结合当前实现，串口打开参数包括端口路径、波特率和协议版本，其中波特率支持 115200 和 460800 两种配置，底层串口采用 8 位数据位、1 位停止位和无校验方式。界面还应显示连接状态和错误信息，使操作人员能够判断当前设备是否已经进入可测试状态。

协议适配紧接在连接之后。所设计的软件系统支持协议 1 和协议 2，两类协议在控制帧长度、反馈帧长度、字段偏移和校验区间等方面存在差异。通信层根据协议版本生成控制帧，并按对应规则解析反馈帧。协议差异被限制在通信层内部后，上层测试流程即可使用统一的反馈数据结构。通信链路和协议对象明确之后，软件才具备判断设备状态的基础。

\subsection{状态确认与基础控制需求}

串口连接成功只是通信入口建立。舵机在进入正式测试前，还需要确认控制链路、执行对象和反馈通道处于可用状态。软件界面设置使能检测入口，连接串口后可检查四路舵机状态，并将检测结果同步到界面显示。当前前端保留了使能检测失败后的重试逻辑，后台负责执行具体判断过程。这个环节把“能否开始测试”的判断放在正式测试之前，可以减少测试运行中才发现设备未使能或反馈异常的情况。

基础控制需求与状态确认相互配合。软件应区分手动控制和自动测试流程，避免两类操作同时占用串口发送通道。控制帧发送成功后，系统还应把设定角度同步到渲染进程，使界面能够同时展示设定值和反馈值。只有当连接、协议和控制状态都明确后，测试任务选择才有稳定的执行前提。

\subsection{测试任务组织与参数输入需求}

测试任务的组织方式直接影响操作过程。通信性能测试关注收发次数、发送间隔和统计结果；控制性能预测试关注噪声采集、阶跃响应和参数估计；时域性能测试关注路径生成、采样窗口和动态指标；频域性能测试关注扫频范围、频率点数和正弦激励采样。这些参数集中在同一界面中会增加操作人员识别当前有效参数的成本，不同测试状态也容易相互干扰。

界面采用按测试类型切换参数面板的方式组织输入。当前界面通过“性能试验选择”下拉菜单加载四类测试面板，每类面板只暴露当前流程所需参数。测试目标、输入参数和后端任务入口由面板绑定，操作人员可以沿着连接、检测、选择、执行的顺序推进测试过程，后续功能扩展也保留在组件边界内。

\subsection{四类测试流程需求}

通信性能测试位于正式测试链路的前端。该测试用于检查串口链路和协议收发过程的基础质量，软件应支持发送测试、接收测试和发送接收联合测试，并统计发送成功率、接收成功率、采样间隔均值、标准差、最大值、最小值和 95\% 置信区间。测试过程还需要提供进度事件、统计事件、完成事件、错误事件和取消操作。通信性能测试的结果决定当前链路是否适合继续承载后续控制和性能分析任务。

控制性能预测试承担参数过渡作用。软件先在静止或小范围运动条件下估计反馈噪声水平，再通过阶跃响应过程估计调节时间和平均运动速度。这些中间量可以用于推导时域测试中的窗口长度、重复次数和等待时间，也可以为频域测试中的采样时长和频点执行时间提供参考。预测试减少了人工经验参数的比例，使正式测试的参数来源更容易追溯。

时域性能测试关注舵机到达目标位置的响应过程。软件根据测试参数生成位置路径，控制舵机依次运动到目标点，采集运动过程中的反馈数据，再计算调节时间、超调量、上升时间、延迟时间、稳态误差和振荡次数等指标。多点测试还要保留位置、方向、步长和重复次数信息，以便观察这些因素对结果的影响。该测试把通信条件和预测试参数转化为可量化的动态性能评价。

频域性能测试从正弦激励下的跟随关系描述舵机响应能力。软件按照用户设置生成扫频点，向舵机发送正弦控制量，采集反馈数据，并用相关分析方法估计输出幅值和相位。测试结束后，系统形成幅频曲线和相频曲线，并提取 -3 dB 带宽、谐振频率、相位裕度和增益裕度等指标。频域测试对采样连续性和激励稳定性要求更高，后台任务、进度事件和图表展示之间需要保持分离。

\subsection{数据展示与结果管理需求}

测试执行过程中，反馈数据需要持续显示。当前系统提供四通道遥测数据和示波器曲线显示，也为时域结果和频域伯德图设置专门图表组件。数据显示服务于两类判断：操作人员可以观察测试是否按预期推进，也可以通过反馈越界、曲线突变或响应迟滞等现象发现异常。

测试结束后，系统还应保存测试配置、关键统计量和分析结果，并支持历史数据加载。结果管理使界面显示后的数据能够继续用于复查和对比。当前软件以测试结果保存和加载为主要目标，图片导出和自动报告生成可作为后续扩展方向。

\section{非功能需求分析}

非功能需求来自这条测试链路中的约束。通信、控制、图表和文件操作虽然出现在不同模块中，但它们在一次测试中会同时发生。后台处理需要保留界面响应，使操作人员能够及时停止测试；错误状态也需要传到界面，便于判断测试结果的可信度。非功能需求据此围绕测试连续性、异常处理、维护成本和结果复查展开。

\subsection{实时性与交互连续性需求}

舵机测试软件同时存在高频数据流和低频控制流。串口反馈、帧解析、控制帧发送确认和曲线刷新属于高频或准实时任务；参数输入、测试项切换、结果查看和文件保存属于低频交互任务。软件应避免高频任务阻塞界面线程，也应避免界面操作干扰串口接收和测试流程。

本系统的实时性需求主要体现在三个方面。串口接收和反馈解析要及时完成，使测试算法能够获得有效数据；界面在测试过程中要保持可操作，至少能够响应停止、取消和状态查看；曲线和指标显示要能够反映当前测试状态。由于完整端到端延迟缺少独立实测支撑，本论文只将其作为设计关注点，不列为已验证性能指标。

\subsection{可靠性与异常可恢复需求}

可靠性需求主要来自硬件通信和自动测试过程。串口连接可能失败或断开，控制帧发送可能超时，反馈帧可能出现半包、粘包、校验错误或字段异常，测试任务也可能因参数非法或硬件状态异常中断。软件需要把这些情况通过错误事件、状态事件和返回值结构传到界面层，让操作人员能够区分连接问题、协议问题、控制问题和测试任务问题。

当前系统在接口层统一使用带 \texttt{success} 字段的返回对象，在事件层提供连接、断开、错误、重连、发送失败和解析错误等事件。串口管理器中还设置了自动重连相关逻辑。这些处理可以支撑当前可靠性需求；长时间稳定运行仍缺少额外实机验证，24 小时连续运行不作为已完成结论。

\subsection{可维护性与扩展性需求}

测试软件包含前端界面、主进程 IPC、串口通信、协议解析、测试核心、数据保存和图表展示等模块。测试项目从通信检查扩展到时域和频域分析后，跨模块传递的数据结构会明显增多。各模块直接共享隐式字段，会增加测试功能修改时对其他流程的影响。

软件采用 TypeScript 描述串口配置、控制数据、测试配置、测试结果和 IPC 事件类型。\texttt{ipc-types.ts} 集中定义请求通道、响应类型和事件类型，接口文档记录接口方向、参数和使用位置。单元测试覆盖串口解析、协议合规、通信测试、预测试、时域测试和频域测试等核心函数，用于检查模块行为是否符合预期。测试覆盖属于工程质量保障内容，不作为主要创新点。

\subsection{可追溯性、易用性与安全性需求}

测试结果需要支持复查。一次完整测试至少要留下测试类型、输入参数、执行时间、关键统计量、指标结果以及必要的原始或中间数据。有了这些记录，测试异常才能继续追溯到通信链路、参数设置、舵机响应或算法处理环节，后续批量分析也有数据基础。

易用性和安全性同样来自现场操作过程。界面需要引导操作人员按连接、使能检测、参数输入、测试执行、结果查看和数据保存的顺序工作，减少无关设置干扰。串口未连接时，软件应禁止发送控制指令；自动测试运行时，系统也要区分手动控制状态；测试任务执行过程中还要保留取消入口。对于时域和频域测试中持续发送激励信号的流程，系统应能够及时停止任务并恢复可控状态。

\section{相关技术}

相关技术的选择需要服务于前述需求。舵机测试软件涉及本地硬件访问、复杂界面、图表展示、高频串口数据处理、前后端数据一致性和多类测试任务调度。围绕这些约束，本系统采用 Electron、Vue3、TypeScript、RS422 串口通信、IPC、Worker、数据可视化和测试框架作为技术基础。

\subsection{Electron 桌面应用框架}

Electron 是本系统的桌面应用基础。该框架允许软件使用 Web 技术构建界面，同时通过主进程访问本地串口、文件系统和系统对话框。放到舵机测试软件中看，渲染进程负责参数输入、状态展示和图表绘制，主进程负责串口通信、文件读写和测试任务调度，界面显示与本地硬件访问由此分开。

国内关于 Electron 数据采集桌面应用的研究说明，Electron 可以用于构建跨平台数据采集软件，并兼顾界面开发效率和本地能力调用\cite{gao2025electron}。数据采集软件相关研究也强调，采集、处理和显示之间的边界会影响实时性和可维护性\cite{stansbury2023autodidaqt,turkmanovic2023highspeed}。这些研究为本系统采用主进程和渲染进程分工提供了技术依据。

\subsection{Vue3 组件化界面与 TypeScript 类型约束}

Vue3 用于组织前端界面。当前软件的界面由通信选择、参数输入、控制面板、数据显示、示波器和数据保存等组件组成，四类测试功能也分别封装为独立参数面板。参数录入、状态切换、实时曲线和结果保存处在不同信息粒度上，组件化组织可以让它们在同一主界面中切换，同时保留各自的参数校验、进度显示和结果展示逻辑。

TypeScript 用于约束跨模块数据结构。串口配置、控制数据、测试配置、测试结果、IPC 返回值和事件对象都可以通过类型定义表达。对于本系统这种前后端通过 IPC 传递数据的桌面软件，类型约束能够减少字段遗漏、参数类型不一致和事件载荷不清晰等问题。它与组件化界面配合后，可以把界面输入、任务配置和后端返回结果纳入同一套类型约束。

\subsection{RS422 串口通信与二进制协议解析}

RS422 是软件与舵机控制器之间的通信链路。桌面测控软件通常需要在设备通信、数据采集、界面显示和结果管理之间建立清晰接口\cite{zhang2017qtflowmeter}。串口分包和缓存处理研究指出，连续数据流中的分包、缓存和校验机制会影响通信稳定性\cite{wu2025serialpacket}；RS422 误码测试系统研究则把上位机交互、总线接口和错误统计纳入同一通信质量评价过程\cite{hu2026rs422ber}。本系统的通信层围绕这些问题组织串口收发、协议解析和错误上报。

当前软件将协议差异拆分为同步字、帧长度、字段偏移和校验区间等定义。串口接收模块负责字节流缓存和帧解析，协议解析模块负责将原始数据转化为统一反馈对象。上层测试功能无需直接处理原始字节流，可使用统一结构组织可视化和指标计算。

\subsection{IPC 与 Worker 异步处理机制}

Electron 应用中的渲染进程和主进程需要通过进程间通信（Inter-Process Communication，IPC）交换数据。当前软件通过预加载脚本暴露 \texttt{window.serialAPI}、\texttt{window.appIpc} 和底层 \texttt{window.ipcRenderer}，其中业务代码主要通过 \texttt{window.serialAPI} 调用串口控制、通信测试、预测试、时域测试和频域测试接口。IPC 通道使用统一的请求和事件命名方式，使测试任务可以通过请求启动，通过事件反馈进度、统计、完成和错误信息。

Worker 在软件工程中通常指独立于主执行上下文的后台工作单元，可以是工作线程、子进程或由框架管理的异步执行环境。它的作用是把耗时或高频任务从界面线程中分离出来，使界面交互不必等待后台计算完成。当前软件中设置了串口 Worker、信号控制 Worker 和渲染 Worker，用于处理串口收发、自动控制和渲染数据整理等工作。该机制对应前文提出的高频数据流与低频交互流分离需求。

\subsection{数据可视化与测试工具}

测试软件需要把反馈数据和指标结果转化为可观察图形。当前系统使用实时示波器曲线展示反馈变化，并通过时域图表和伯德图展示正式测试结果。频域测试中的伯德图采用幅频和相频双图形式，时域测试图表则围绕误差、位置、方向和响应曲线组织结果。操作人员可以在测试执行期间看状态，也可以在测试结束后复查结果。

工程验证方面，项目使用 Vitest 对核心模块进行单元测试。Vitest 是面向 Vite 工具链的 JavaScript/TypeScript 测试框架，可用于编写和运行函数级、模块级测试。当前测试文件覆盖串口解析、协议合规、信号处理、通信性能测试、控制性能预测试、时域测试和频域测试等模块。单元测试在离线条件下检查算法和协议处理逻辑，实机脚本则用于验证后端通信和硬件链路。

\section{本章小结}

本章从测试流程出发，将精密舵机测试软件的需求归纳为通信接入、状态确认、任务组织、四类测试、数据显示和结果管理等环节。通信和协议适配提供数据入口，使能检测和基础控制确认执行条件，预测试给时域和频域测试提供参数来源，正式测试结果再进入可视化和留档过程。

围绕这条测试链路，软件还要满足实时性、可靠性、可维护性、可追溯性、易用性和安全性等非功能要求。Electron、Vue3、TypeScript、RS422 串口通信、IPC、Worker、数据可视化和测试工具分别对应本地硬件访问、界面组织、数据约束、通信解析、异步处理和工程验证需求。以上分析为第三章的总体架构设计提供需求边界和技术依据。
